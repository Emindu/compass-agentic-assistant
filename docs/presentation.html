Compass

An agentic knowledge assistant for Commercial Bank — POC

  • Answers employee questions over 25 internal documents, with citations
  • Shows every internal step: routing, retrieval scores, plan code, tool calls, validations
  • Role-based access enforced in code paths, at every layer

All bank data in this POC is fictional mock data. · Disagree with a choice? Six ADRs in docs/adr/ explain the reasoning.

Context

What this POC is and how effort was spent

Internal knowledge assistant for bank employees: policies, runbooks, incident reports, specs, meeting minutes. The brief grades ten areas, so the plan spends effort where the marks are — agent architecture, RAG, LangGraph and RLM carry 60%.

Everything else is deliberately simple but real: three demo users behind JWTs, one SQLite checkpointer, a local BM25 fallback, Docker Compose for the demo.

Grading weights used as the build priority order:

Agent architecture20%
RAG design15%
LangGraph usage15%
RLM10%
Security & guardrails10%
Observability10%
Async · RBAC · quality · docs4×5%

Planted ground truth, not vibes

The 25-document corpus has known patterns planted for verification: 8 payment incidents with 3 recurring root causes, two versions of a certificate runbook, a draft with a wrong preliminary cause, a decoy non-payment incident, a poisoned document with an injected instruction. evals/ground_truth.json pins the expected answers.

Time-boxed build

Planned as one working day: scaffold → corpus → hybrid retrieval → graph + API → RLM → UI + RBAC → guards → docs → 14:30 code freeze → record. Small conventional commits per block, so the history reads as a build log.

Cut line, stated up front

Long-term per-user memory, feedback loop, learned reranking and the full eval harness were cut on purpose and named as next steps — never RLM, RBAC or tracing.

Agent architecture

Supervisor + specialists, one typed state, contained failures

START → load_memory → input_guard ─┬─(blocked)────────────────→ finalize └─(allowed)→ supervisor supervisor ─┬─(docs)─────→ retrieval → response ├─(research)→ research → response ├─(tools)────→ tools ─┬───→ response │ └─(also docs)→ retrieval → response └─(smalltalk/out of scope)→ response response → validator ─┬─(invalid, retries left)→ response └─(valid/out of retries)→ finalize → update_memory → END

Node names exactly as in app/agents/graph.py. Conditional edges branch on typed values — GuardVerdict, RouteDecision, ValidationResult — never on parsed text.

Supervisor = a typed decision, not prose

RouteDecision carries intent (7 types), specialist agents, a standalone rewritten search query (resolves pronouns from history), department scope and a one-sentence reasoning that shows in the UI.

Failure containment: instrumented

Every node is wrapped: a raise becomes an AgentError in state plus an error event, and the node's fallback update runs instead. Supervisor down → plain document search. Model down → answer lists sources. One failing agent degrades the answer; it never crashes the request.

Validator loop

Deterministic citation check between response and finalize: every bracketed id must be a retrieved chunk. Up to 2 retries with issues fed back, then unknown citations are stripped with a caveat — or the answer is replaced with an honest "couldn't find".

RAG

Hybrid retrieval with access control the prompt cannot widen

DenseSparse
Indexcompass-densecompass-sparse
Model (Pinecone-integrated)llama-text-embed-v2 (cosine)pinecone-sparse-english-v0 (dot)
Catchesparaphrases: "why did card payments fail because of TLS"exact terms: HikariPool, INC-2026-0214

Fusion — both lists max-normalised, then weighted:

fused = alpha × dense_norm + (1 − alpha) × sparse_norm # HYBRID_ALPHA = 0.6

One explainable knob; both raw scores stay visible in the activity panel. Top-8 with at most 2 chunks per document, so several sources get cited. Both sides over-fetch top_k × 3 for fusion material.

RBAC is a hard metadata filter

Access comes from the JWT role, never the prompt: access_rank <= clearance is always the first filter clause (viewer→internal, analyst→confidential, admin→restricted). One namespace per department is a scoping convenience, not a security boundary.

Degradation that never widens access

One index down → the other answers alone. Both down (or FAULT_PINECONE=true) → a local rank_bm25 index over the same chunks answers with the identical filter set. Results carry a degraded flag and a user-facing note.

Citations

Chunks are section-aware (split on ##, packed to 1200 chars, deterministic ids) with a contextual header. Answers cite [DOC-ID#NN], e.g. [RB-PAY-003-V2#03]; the UI shows doc_id › section. ~0.4 s warm retrieval; connections warmed at API start-up.

RLM — recursive language model

Don't stuff documents into context. Write a program that gathers evidence.

plan → execute → Send ×N analyse_batch → reduce │ └─ follow-up (depth < 2) ────────┘ plan code model writes a ≤60-line Python search plan execute plan runs in a sandboxed subprocess; primitives run in the PARENT with the user's clearance map one fast-model call per batch, in parallel (Send) — each batch sees only its own chunks reduce main model: themes + counts, citing chunk ids

Evidence cannot be invented: only chunk ids the primitives actually returned are accepted into batches; findings citing anything else are dropped, and the parent's evidence becomes the citable retrieved set for the response agent.

Primitives (parent-side, clearance re-derived from the JWT)

list_documents() metadata only · get_sections() named sections (forbidden = missing = [], so plans can't probe) · search() hybrid retrieval · llm_query() budgeted recursive sub-call to the fast model.

Sandbox defence in depth

1 Static AST allow-list (imports, no dunders, no eval/exec/…) · 2 restricted builtins + runtime import re-check · 3 empty child env, rlimits (CPU 20 s / 512 MB / fd / filesize) · 4 unshare -rn user+network namespace when the kernel allows. Production upgrade: gVisor / Firecracker.

Budgets bound the worst case

Per run: 30 s wall clock, ≤40 primitive calls, ≤200 KB result, ≤8 batches × ≤8 chunks, llm_query ≤12 calls / 12k chars. Depth capped at 2; a failed plan gets one corrective retry with the error fed back.

Compass — internal6 / 16
RLM — the hard-won lesson

Why the planner is forced to select by metadata, not keywords

In testing, plans that filtered candidate documents by keywords in titles — or by service name — silently dropped relevant documents. The gap between the user's words and the corpus runs deep:

User asks aboutDocument says
"card payment failures because of TLS"certificate_expired on cefts-adapter; title: "Weekend CEFTS connectivity loss after client certificate lapsed"
"recurring root causes of payment outages"Root causes described as "client certificate lapsed", "connection pool exhaustion", "immediate retries without backoff" — no title contains those words

So the planner is instructed — in the system prompt and again in the user-role message, because the code model weighs it more — to:

  1. explore with list_documents() metadata filters (type, department, dates, status) only,
  2. read the relevant sections of every candidate,
  3. use keyword search() only when metadata cannot narrow, and let batch analysis judge relevance.

This also caps context: each batch call sees a few chunks, not the corpus. Recorded in docs/DESIGN.md (RLM section) with the example above.

7Citation validatordeterministic set difference vs retrieved ids; retry ≤2, then strip or replace
8Output guardblocks financial advice, secret shapes (redacted), system-prompt leakage; warns on brand-voice issues, external links
9Sandbox + approvalRLM code runs only sandboxed; admin tools pause on interrupt() — Approve/Reject via admin-only endpoint

Design rule: guards are graph nodes, so verdicts are state, typed branches and events — not middleware. A fooled model cannot reach forbidden tools or data; control lives in code.

Derived from the verified JWT only

UserContext (id, name, role, department, clearance) is rebuilt from JWT claims each turn. Chat text never sets identity, scope or access.

Demo-friendly denials

A viewer asking for analytics gets a denied event in the panel and falls back to document search; an admin request from a non-admin gets a deterministic refusal. Both paths are scripted and unit-tested.

LLM setup

Three model roles, shared limits, explicit fallbacks

RoleModelUsed forFallback
mainmistral-large-latestsupervisor routing, final answer, RLM reduce, tools planning→ fast
fastmistral-small-latestinput guard, RLM batch map, summaries, llm_query—
codecodestral-latestRLM planner (Python search plans)→ CODE_LLM_FALLBACK → main

One factory rule: every LLM call goes through app/core/llm.py — ainvoke_llm / ainvoke_structured / astream_llm — never a raw client. That is where the shared semaphore, timeouts, retries and fallback chains live.

One workspace, one budget

All calls share one asyncio semaphore (LLM_MAX_CONCURRENCY=3), including streams. Retries: tenacity, transient errors only (429/5xx/timeout), exponential backoff with jitter; a 4xx fails fast. Slots are taken per attempt so backoff never blocks other calls.

Structured output, hardened

Function-calling structured output everywhere; if the provider rejects the schema or the parse fails, a JSON-mode prompt with the schema is the fallback, so a bad structured call still succeeds.

Why these trade-offs

Free-tier limits shape concurrency design; open-weight lineage means the bank could self-host the same model families for data residency without redesigning the graph. Lock-in is one env change (init_chat_model).

Observability

A trace is the product: every run is explainable after the fact

LangSmith

Every chat = run compass_chat, tagged role:{role} + metadata user/thread/request-id. LLM calls named llm:main|fast|code. Retrieval is @traceable retrievers whose outputs render as documents. RLM subgraph nests under the research node, so plan → batches → reduce reads as one tree. A shared fault flag makes the fallback route visible in traces.

structlog

JSON on stdout with a request_id contextvar on every line (honours inbound x-request-id), user_id/role bound per request, one http_request line per call, structured events for fallbacks, retries, guard verdicts, rate limits. Log line ↔ trace join on request id.

The activity panel renders 14 typed SSE events, live:

node_start node_end route retrieval tool_call research memory validation guardrail approval token answer error done
  • Routing reasoning, one sentence, in the panel
  • Retrieval hits with dense / sparse / fused scores per source
  • The RLM's generated Python plan, sandbox outcome, batches
  • Tool calls with denials, previews, pending-approval payloads
  • Sources, degraded notes and per-node timings on every answer

Reducers in ui/activity.py are pure and unit-tested — panel formatting never trusted to a live LLM.
